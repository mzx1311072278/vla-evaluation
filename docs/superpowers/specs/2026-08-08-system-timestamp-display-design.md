# 系统时间戳显示设计

## 1. 目标

统一修正数据集、导入任务、评测任务和评测报告中的系统时间显示。所有用户可见的日历时间均转换为北京时间，使用 24 小时制并精确到秒，例如 `2026-08-08 18:35:42（北京时间）`。

本功能继续在 `feature/vla-eval-web-vlm-api-backend` 分支实施，`main` 不修改，无关的 `uv.lock` 不纳入提交。

## 2. 边界与不变项

- 不修改、迁移或回写任何数据集文件，包括视频、Parquet、JSON、YAML、CSV 和附件。
- 不修改数据集内部的 `created_at` 或其他采集元数据。页面上的“导入系统时间”来自网站数据库，不等同于数据采集时间。
- 数据库中的系统时间继续使用带时区的 UTC；现有记录不做数据迁移。
- API 继续返回带时区的 ISO 8601 UTC 时间，保持现有程序调用契约。
- Episode 的 `from_timestamp`、`to_timestamp`、`rough_start_time` 和 `rough_end_time` 是视频相对秒数，不属于日历时间，不做时区转换。
- 报告只读取已有评测产物，不重新计算核心指标。

## 3. 方案选择

采用“UTC 存储、北京时间展示”的统一方案：

1. 数据库模型继续通过 `UTCDateTime` 写入和读取 UTC。
2. API 继续输出 ISO 8601 UTC，例如 `2026-08-08T10:35:42+00:00`。
3. Web 页面和 Markdown 报告通过同一组时间工具转换为 `Asia/Shanghai`，显示为 `2026-08-08 18:35:42（北京时间）`。
4. 报告目录和文件名中的日期统一按北京时间计算，避免部署服务器所在时区改变日期。

不采用在各模板中直接调用 `strftime` 的方案，因为容易遗漏页面且无法保证时区转换一致。也不把数据库改存北京时间，因为这会破坏 UTC 契约并引入迁移风险。

## 4. 时间工具

新增一个无状态的时间工具模块，集中负责：

- 使用标准库 `zoneinfo.ZoneInfo("Asia/Shanghai")` 定义北京时间，不依赖宿主机时区或第三方库。
- 将带时区的 `datetime` 转换为北京时间。
- 将系统时间格式化为固定的 24 小时制文本，精确到秒并附带“北京时间”标识。
- 返回当前北京时间，供报告生成日期和默认输出目录命名使用。
- 对 `None` 返回 `—`；系统内部出现无时区 `datetime` 时沿用现有数据库兼容策略，按 UTC 解释后再转换。

所有页面模板通过统一的 Jinja 过滤器调用该工具，禁止继续直接对系统时间执行 `strftime`。报告生成代码直接调用同一工具，避免 Web 和下载报告使用不同规则。

## 5. 页面展示

### 5.1 数据集

- 数据集列表增加“导入系统时间”，显示 `Dataset.created_at` 的北京时间；现有“最新创建/最早创建”排序与该列一致。
- 数据集详情显示“导入系统时间”和“最后更新时间”。这些字段只描述网站记录，不描述数据采集时间。
- 数据集归档时，在详情页显示归档时间；归档元数据仍以 UTC 保存在数据库 JSON 中。
- 最近评测列表中的创建时间改为统一北京时间格式。

### 5.2 导入任务

- 导入任务列表增加“创建时间”。
- 导入任务详情显示“创建时间”和“最后更新时间”。
- 任务运行期间的 HTMX 自动刷新继续更新最后更新时间。

### 5.3 评测任务

- 评测任务列表的“创建时间”改为北京时间并精确到秒。
- 评测任务详情显示“创建时间”和“最后更新时间”。
- 已归档任务详情显示归档时间。

### 5.4 网页报告

- 报告页显示评测任务创建时间和最后更新时间，均来自数据库系统记录。
- 报告中的数据证据时间和视频相对时间保持原有语义，不能用任务时间替代或伪造。

## 6. Markdown 报告与评测产物

- 报告配置章节分别标明数据记录时间和报告生成时间，不再使用含义不清的“日期”。
- 数据记录时间来自 `session.json` 的 `created_at`；只在报告文本中转换显示，不修改源文件。
- LeRobot 数据集没有 `session.json` 时，合成会话的 `created_at` 继续取数据集目录修改时间，但先形成带时区的绝对时间，不能依赖服务器本地时区。
- 报告生成时间取实际生成时刻并按北京时间显示。
- 默认报告目录日期和 `report_YYYYMMDD.md` 文件名按北京时间计算。
- 对已有报告文件不做批量重写；重新生成报告时应用新规则，网页中的任务时间立即按新规则展示。

## 7. 错误处理与兼容性

- 数据库读取出的旧 SQLite 无时区值按现有约定视为 UTC，避免重复增加 8 小时。
- 缺失的可选系统时间显示 `—`，页面不因空值报错。
- 数据记录时间若缺失或格式非法，报告生成沿用现有输入校验并给出明确错误，不猜测本地时区。
- 时区转换失败不得修改原始值或数据集内容。
- API 的 `updated_at` 等字段继续以 `+00:00` 结尾，现有客户端无需修改。

## 8. 测试与验收

实施时先增加能够复现问题的失败测试，再修改实现。

自动化测试覆盖：

- 固定输入 `2026-08-08 10:35:42+00:00`，页面必须显示 `2026-08-08 18:35:42（北京时间）`。
- 已带 `+08:00` 的输入不得重复增加 8 小时。
- 数据集列表和详情、导入任务列表和详情、评测任务列表和详情、归档时间及网页报告。
- Markdown 报告中的数据记录时间、报告生成时间和按北京时间生成的文件名。
- API 仍返回 UTC ISO 8601 时间。
- Episode 视频相对时间的展示和计算保持不变。
- 数据集目录和文件内容在测试前后保持不变。

最终运行聚焦测试、完整测试、Ruff 和 `git diff --check`。本地站点启动后，使用真实页面检查 24 小时制、秒数、北京时间标识及窄屏布局，确认时间文本不重叠。
